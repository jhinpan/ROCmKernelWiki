Motivation
Provide a shippable way to measure hipBLASLt GEMM performance under CU contention — i.e. with a fixed number of CUs occupied by another resident kernel. This makes it easy to study how the library and its kernels behave when fewer CUs are available (dynamic/StreamK scheduling, co-tenant scenarios) without modifying hipblaslt-bench.
Technical Details
Adds clients/scripts/cotenant/:

hipblaslt-cotenant-kernel (HIP) — a persistent, compute-free kernel that occupies exactly N CUs by pinning one workgroup per CU via a runtime-sized dynamic-LDS reservation (the runtime equivalent of TensileLite's MaxOccupancy: 1). Each workgroup reports in through a system-scope atomic counter in host-pinned memory, so the host confirms full residency (READY) rather than guessing a settle time.
hipblaslt-cotenant (stdlib-only Python launcher) — locates/builds the kernel, launches it on --cus N, waits for READY, runs an arbitrary command (e.g. hipblaslt-bench) under that contention, and always tears the cotenant down on exit.
