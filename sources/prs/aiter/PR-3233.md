# Fix TP4 bf16 MLA persistent dispatch

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#3233](https://github.com/ROCm/aiter/pull/3233) · **Merged:** 2026-05-16 · **Author:** @XiaobingSuper

**Inclusion reason:** kernel path 'csrc/py_itfs_cu/asm_mla.cu'; keyword 'kernel'

## Summary (from upstream PR description)

Summary

Route gfx950 gqa_ratio=32 bf16/bf16 persistent MLA decode to the existing qh32 persistent kernel.
Prevent the generic gfx950 bf16 persistent remap from overriding TP4 to the qh64 qseqlen1 kernel.
Keep sparse MLA persistent/work-stealing enabled; this is not a fallback or feature disable.

Problem
DeepSeek-V3.2 TP4 sparse MLA decode regressed in accuracy after enabling the AITER sparse persistent/work-stealing path. TP8 stayed accurate because TP8 uses gqa_ratio=16, while TP4 uses gqa_ratio=32.
For TP4 bf16/bf16 decode, the current dispatch first leaves gqa_ratio=32 as-is, but the later gfx950 persistent remap also matches because gqa_ratio > 16. That remap changes the dispatch target to:

config_gqa_ratio = 64
config_max_seqlen_q = 1
mla_a16w16_qh64_qseqlen1_gqaratio64_v3_ps.co

That means TP4 qh32 decode runs through the qh64 persistent kernel path. In full vLLM accuracy testing this produced a large GSM8K drop, around 0.90 exact match instead of the expected ~0.946+ range.
Fix
AITER already ships a gfx950 bf16/bf16 persistent kernel for the TP4 shape:
bf16,bf16,32,1,4,...,mla_a16w16_qh32_qseqlen4_gqaratio32_ps.co
