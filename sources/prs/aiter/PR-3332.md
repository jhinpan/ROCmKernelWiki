# [dtypes] add gfx1200 / gfx1201 (RDNA4) to FP8 dtype map

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#3332](https://github.com/ROCm/aiter/pull/3332) · **Merged:** 2026-05-27 · **Author:** @carlushuang

**Inclusion reason:** keyword 'gemm'

## Summary (from upstream PR description)

Summary
aiter/utility/dtypes.py:9 has a per-arch map for the FP8 torch dtype. On any arch not in the map, get_dtype_fp8 returns the uint8 fallback, which silently breaks every downstream consumer that depends on dtypes.fp8 being a real float8 type.
In particular, torch_gemm (aiter/tuned_gemm.py:411) only handles float8 inputs:
try:
    torch._scaled_mm(inp, weights.t(), ...)
except RuntimeError:
    F.linear(inp.to(fp32), weights.to(fp32)) * scale_a * scale_b

On uint8 input, _scaled_mm rejects with "Invalid scaling configuration" and the fallbacks uint8.to(fp32) reinterprets FP8 bytes as integers 0..255 — output is garbage. Verified on gfx1201: a 4x64x128 GEMM with ones scales returns ~1.8M for elements that should be O(1).
Add gfx1200 / gfx1201 to the map with torch.float8_e4m3fn (same as gfx950 and gfx1250). With that, torch_gemms fallback runs as F.linear(float8.to(fp32), float8.to(fp32)) * scales — dequantizes correctly.
Test plan

 Direct test: tgemm.mm(x_fp8, w_fp8, scale_a=1, scale_b=1) on gfx1201 vs BF16 F.linear — max abs diff 1.36 (typical FP8 quantization noise; was 2.1M before this fix).
 End-to-end gsm8k 5-shot n=200 on RX 9070 XT via ATOM: Mistral-3-8B 0.790/0.795, Q
