# ci(release): add manylinux2_28+ROCm builder path with auditwheel gate (fixes #2843 long-term)

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#2851](https://github.com/ROCm/aiter/pull/2851) · **Merged:** 2026-04-22 · **Author:** @sunway513

**Inclusion reason:** kernel path 'csrc/kernels/gated_rmsnorm_quant_kernels.cu'; keyword 'attention'

## Summary (from upstream PR description)

Summary
Add an opt-in use_manylinux path to aiter-release.yaml that builds wheels inside pytorch/manylinux2_28-builder:rocmX.Y — the same image lineage that PyTorch's official ROCm wheels are built on (AlmaLinux 8, glibc 2.28, gcc-toolset-13 with static libstdc++). This produces wheels that obey the manylinux_2_28 ABI contract and are dlopen-safe inside vllm/vllm-openai-rocm (Ubuntu 22, max GLIBCXX_3.4.30).
This is the proper long-term fix for #2843. The legacy rocm/pytorch:rocm7.2_ubuntu24.04_py3.12_* image is Ubuntu 24 + GCC 13, so its wheels reference GLIBCXX_3.4.31, which is unavailable inside vLLM's Ubuntu 22 base. The dlopen failure is silently swallowed by aiter/__init__.py's broad try/except and surfaces downstream as ImportError: cannot import name 'flash_attn_varlen_func' from 'aiter'.
Why manylinux

Standard Python packaging contract (PEP 600 manylinux_2_28).
Identical toolchain to upstream PyTorch ROCm wheels (torch==2.11.0+rocm7.2).
AlmaLinux 8 base (glibc 2.28) + gcc-toolset-13 with static libstdc++ linkage means produced .so files only reference low GLIBCXX symbols — wide consumer compatibility.
Available image tags already published: pytorch/manylinux2_28-builder:ro
