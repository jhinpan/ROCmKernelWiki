# [csrc/opus] add synchronous fallback to _async_load for non-buffer-to-LDS archs

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#3336](https://github.com/ROCm/aiter/pull/3336) · **Merged:** 2026-05-27 · **Author:** @carlushuang

**Inclusion reason:** kernel path 'op_tests/opus/device/setup.py'; keyword 'fp8'

## Summary (from upstream PR description)

Summary
opus::_async_load in csrc/include/opus/opus.hpp used two implementations:

#elif __clang_major__ >= 20 -> __builtin_amdgcn_raw_ptr_buffer_load_lds
#else -> llvm_amdgcn_raw_buffer_load_lds

Both rely on a buffer-load-directly-to-LDS hardware instruction. CDNA archs (gfx940 / gfx941 / gfx942 / gfx950) have it via the vmem-to-lds-load-insts target feature; RDNA archs (gfx10xx / gfx11xx / gfx12xx) do not. On gfx1201 (RDNA4) the modern path fails to compile with needs target feature vmem-to-lds-load-insts, and the legacy path fails with Cannot select: intrinsic %llvm.amdgcn.raw.buffer.load.lds. This means any aiter kernel that pulls in opus.hpp (module_quant, module_rmsnorm_quant, ...) refuses to build on gfx12xx, even when the specific kernel never actually instantiates _async_load.
Fix

Narrow both buffer-to-LDS paths to CDNA arches that have the feature.
Add a #else synchronous fallback that works on every arch: load to a VGPR via the existing _load<vec, aux>, then store to LDS via a plain pointer write. Functionally equivalent; loses the latency-hiding benefit of the buffer->LDS direct path, but those archs do not have that hardware anyway.

Test plan

 CDNA behavior unchang
