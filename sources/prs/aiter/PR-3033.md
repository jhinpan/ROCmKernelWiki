# Fix sqrsum store race condition in mhc_pre_gemm_sqrsum_kernel

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#3033](https://github.com/ROCm/aiter/pull/3033) · **Merged:** 2026-05-06 · **Author:** @kkHuang-amd

## Summary (from upstream PR description)

Motivation
When running DeepSeek-V4 inference with SGLANG_OPT_USE_AITER_MHC_PRE=true, GSM8K accuracy intermittently drops below 0.9, while the torch-native implementation (hc_pre_torch_impl + hc_split_sinkhorn) consistently achieves > 0.91. The root cause is a race condition in the mhc_pre_gemm_sqrsum_kernel that corrupts RMS normalization values.

After cross_row_sum_4() reduces sqrsum across the 4 k-groups, all 4 lanes handling the same row hold the identical reduced value. The bug: the sqrsum store used raw lane_id for the output index:





// BUG: lane_id can be 0-63, not just 0-15
if ((warp_id * mfma_m + lane_id < m_oob)) {
    sqrsum[... + warp_id * mfma_m + lane_id] = sqrsum_;
}
This caused warp 0's lane 16 (which holds row 0's sqrsum) to write to index 16 (which should hold row 16's sqrsum from warp 1). The race between warp 0 lane 16 and warp 1 lane 0 is non-deterministic — whoever writes last wins, leading to intermittent corruption of the RMS normalization values.
