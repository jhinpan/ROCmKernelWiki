# [TRITON] fix torch.compile graph break in arch_info.get_arch()

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#2688](https://github.com/ROCm/aiter/pull/2688) · **Merged:** 2026-05-02 · **Author:** @lauri9

**Inclusion reason:** kernel path 'aiter/ops/triton/utils/_triton/arch_info.py'; keyword 'gemm'

## Summary (from upstream PR description)

Motivation
When any AITER Triton operator is used inside a torch.compile(fullgraph=True) region, the call to triton.runtime.driver.active.get_current_target().arch inside arch_info.get_arch() causes a graph break. Dynamo cannot symbolically trace this opaque runtime call, so it falls back to eager execution for that subgraph. With fullgraph=True this surfaces as a hard torch._dynamo.exc.Unsupported error; without it, the graph is silently split, losing compilation benefits.
The graph break potentially affects every operator that depends on arch_info. There are approximately 25 call sites spanning attention kernels (sage, lean_atten, mha, hstu, extend, mla_decode_rope), GEMM kernels (a8w8, afp4wfp4, a16wfp4, a8wfp4, blockscale, batched variants, gmm), MoE (quant_moe, routing), gluon (pa_decode, gemm variants), fusions (fused_bmm_rope_kv_cache), and utility modules (types, gemm_config_utils, moe_config_utils). All of these call get_arch() to select tuned kernel configs or check hardware feature availability.
