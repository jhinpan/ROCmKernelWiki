# [Bugfix][CKTile] Use local expert ids for MoE bias activation

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#3208](https://github.com/ROCm/aiter/pull/3208) · **Merged:** 2026-05-19 · **Author:** @XiaobingSuper

**Inclusion reason:** kernel path 'aiter/fused_moe.py'; keyword 'attention'

## Summary (from upstream PR description)

Summary

Fix the GPT-OSS MoE EP crash where CKTile two-stage bias activation could index local bias tensors with global expert ids and hit hipErrorIllegalAddress.
Make Opus MoE sorting emit local_topk_ids on GPU, including the multi-phase MP sorter.
Add a fused gelu_and_mul_bias activation kernel and route the bias GELU path through fused activation instead of a Python helper.

Problem
With expert parallelism enabled, topk_ids contains global expert ids. CKTile split-k/two-stage activation receives bias tensors that are local to the current rank, so using global ids as bias row indices can read past the local bias allocation. This shows up in ATOM GPT-OSS TP+EP startup/cudagraph capture as a GPU illegal memory access.
Solution

moe_sorting_opus accepts an optional local_topk_ids output and fills it directly from the expert mask/cumulative local expert mapping.
Both Opus sorting policies now support local id emission: the single-kernel path and the multi-phase MP path.
fused_moe_ requires sorter-provided local ids for the CKTile bias path; CK sorting falls back to Opus when local ids are needed instead of silently using the unsupported path.
