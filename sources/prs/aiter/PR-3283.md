## Summary (from upstream PR description)

Motivation
This PR improves gfx950 batched GEMM benchmark coverage and tunes several batched GEMM config files to reduce performance regressions observed when comparing the TOT Triton compiler stack against the golden compiler stack.
The regression methodology follows the agreed timing rule:
Ignore shapes where golden_time < 4 us.

Otherwise, flag regression iff:
tot_time > 1.005 * golden_time + 0.5 us
Timing is measured with rocprofv3 --kernel-trace --stats, using repeated runs and the 5% stability heuristic:
Run 3 reps.
If all 3 are within 5%, average all 3.
Otherwise, use the closest pair within 5%.
If no pair is within 5%, run up to 5 reps and apply the same rule.
Before this tuning work, the batched GEMM comparison had 22 regressions in total. After the config tuning and benchmark coverage updates in this PR and the fix for batched_gemm_a8w8, we have cleared all the regressions. The final full run produced one threshold-boundary batched_gemm_afp4wfp4 flag, but a targeted recheck of that exact shape reclassified it as OK / measurement-noise-boundary. For the raw numbers and status of each shape and individual test case, refer to the performance spreadsheet.
