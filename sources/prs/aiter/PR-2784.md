# Fix LDS Exhaustion in `fused_gemm_afp4wfp4_a16w16` for ASYNC_COPY Enabled

**Repository:** [ROCm/aiter](https://github.com/ROCm/aiter) · **PR:** [#2784](https://github.com/ROCm/aiter/pull/2784) · **Merged:** 2026-04-22 · **Author:** @nidal567

**Inclusion reason:** kernel path 'aiter/ops/triton/_triton_kernels/gemm/fused/fused_gemm_a8w8_blockscale_a16w16.py'; keyword 'gemm'

## Summary (from upstream PR description)

Motivation
This PR cleans a line in a previous code for consistency and fixes OutOfResources: out of resource: shared memory failures in the fused_gemm_afp4wfp4_a16w16 Triton kernel when running with TRITON_HIP_USE_ASYNC_COPY enabled (which is the default in the current Triton compiler and has caused lots of breakage (see here). The failures occur for specific shape combinations: N1=512, N2=256, K=7168 with M ∈ {64, 8192} and non-preshuffled kernel path (fp4_shuffle=False).
Experimentally, reducing BLOCK_SIZE_M in the M_LEQ_64 and any config buckets is an alternative path to the same fix, but reducing num_stages is the cleaner and less risky change since it does not alter the tile geometry or affect the config files how they were desired to be tuned by the original implementation.
Technical Details
Reduce num_stages from 2 to 1 in the two affected config buckets in:
aiter/ops/triton/configs/gemm/gfx950-FUSED-GEMM-AFP4WFP4-A16W16-N4=512-N16=256-K=7168.json
Specifically (key values):
M_LEQ_64: num_stages: 2 -> 1
any: num_stages: 2 -> 1
With num_stages = 1, there is no double-buffering - only one copy of each tile buffer lives in LDS at a time, halving the staging buffer LDS requireme
