# [dotOp] [rocMLIR] [Upstream] Upstream sync after IFU04262023

**Repository:** [ROCm/triton](https://github.com/ROCm/triton) · **PR:** [#216](https://github.com/ROCm/triton/pull/216) · **Merged:** 2023-05-15 · **Author:** @zhanglx13

**Inclusion reason:** kernel path '.github/workflows/torchinductor/scripts/check_acc.py'; keyword 'gemm'

## Summary (from upstream PR description)

This PR tries to sync the triton-mlir and dot-rocMLIR branch after

#200

The main challenge in this sync comes from the follow upstream PR:

triton-lang#1502

in which func::FuncOp is replaced with triton::FuncOp since they do not like the restrictions of inlining behaviors imposed by func::FuncOp.
This affects dot-rocMLIR much more than the upstream, since a lot of rock transforms (rock-blockwise-gemm-to-threadwise, rock-threadwise-gemm-lowering, rock-sugar-to-loops, rock-clean-math, and rock-buffer-load-merge) works with func::FuncOp. In particular, rock-sugar-to-loops relies functions in Affine/Utils/LoopUtils.cpp to do loop unrolling, which work on func::FuncOp (promoteIfSingleIteration()).
This PR copies affected functions from Affine/Utils/LoopUtils.cpp into lib/Dialect/Rock/Transforms/SugarToLoops.cpp and put them in mlir::rock namespace.
The hope is that upstream LLVM has a better inlining behavior for func::FuncOp and upstream triton will revert the changes and goes back to func::FuncOp from triton::FuncOp. Therefore, we can also get rid of this not-so-elegant workaround.
