# [GEMM] [Tuning] Merge split_k and non split_k kernels in GEMM tuning script

**Repository:** [ROCm/triton](https://github.com/ROCm/triton) · **PR:** [#344](https://github.com/ROCm/triton/pull/344) · **Merged:** 2023-09-28 · **Author:** @zhanglx13

**Inclusion reason:** kernel path 'scripts/amd/gemm/matmul.py'; keyword 'gemm'

## Summary (from upstream PR description)

This PR merges the two kernels in triton/scripts/amd/gemm/matmul.py so now we can use SPLIT_K=1 to represent the non split_k kernel.
Previously doing this led to worse performance for large GEMMs that do not need split_k. And this is because split_k kernels set SPLIT_K as the second dim in the grid, which is used to compute offs_k as
offs_k = pid_z * BLOCK_SIZE_K + tl.arange(0, BLOCK_SIZE_K)
a_ptrs = a_ptr + offs_am[:, None] * stride_am + offs_k[None, :] * stride_ak
This adds "noise" in the offset of the k dim, which is the fastest changing dim of input A. As summarized in the pointer arithmetic investigation, this prevents the LLVM backend to generate maximal vectorized global_load instructions.
This PR also add num_stages=0 to the full tuning space. This doubles the tuning time. But I plan to apply @alefimov-amd's multithreading trick in #310 to reduce the tuning time.
