# [Bugfix] [ROCm] [DSV4] Fix AITER MXFP4 MoE weight loading and shuffle…

**Repository:** [vllm-project/vllm](https://github.com/vllm-project/vllm) · **PR:** [#42595](https://github.com/vllm-project/vllm/pull/42595) · **Merged:** 2026-05-29 · **Author:** @MHYangAMD

## Summary (from upstream PR description)

… for FlyDSL kernels
Purpose
Fix three bugs in the AITER MXFP4 MoE integration path that caused garbled output when using --moe-backend aiter with DeepSeek-V4 on ROCm (gfx950).
Bug 1 — TP weight loading offset with padded dimensions:
_load_w13 / _load_w2 used the padded shard_size (512, rounded up from 384 by mxfp4_round_up_hidden_size_and_intermediate_size) to compute checkpoint offsets. With TP=8, ranks 6 and 7 computed start_offset = 512 * 6 = 3072 which equals or exceeds the checkpoint's 3072 rows, so those ranks loaded zero weights. Fix: derive loaded_per_rank from the actual checkpoint dimension divided by tp_size.
Bug 2 — Incorrect de-interleave in convert_weight_to_mxfp4_moe_kernel_format:
The AITER branch applied a view(e, n//2, 2, k).permute(0,2,1,3) de-interleave assuming the input w13 was stored as interleaved [g0, u0, g1, u1, ...] (as in the GPT-OSS checkpoint format). However, the standard _load_w13 path loads w1 and w3 separately into [gate_all, up_all] layout. Applying de-interleave on already-separated data garbled the rows. Fix: remove the de-interleave step for the standard checkpoint path.
Bug 3 — Wrong shuffle functions for FlyDSL kernels:
vLLM used shuffle_wei
