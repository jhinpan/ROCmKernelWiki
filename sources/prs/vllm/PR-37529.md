# [ROCm] Enable MORI EP for unquantized MoE with AITER backend

**Repository:** [vllm-project/vllm](https://github.com/vllm-project/vllm) · **PR:** [#37529](https://github.com/vllm-project/vllm/pull/37529) · **Merged:** 2026-03-30 · **Author:** @pinsiangamd

**Inclusion reason:** kernel path 'vllm/model_executor/layers/fused_moe/all2all_utils.py'; keyword 'gemm'

## Summary (from upstream PR description)

Purpose
Fix silent degradation when using MORI EP (--all2all-backend mori) with unquantized (BF16) MoE models and the AITER expert backend on ROCm.
Currently, UnquantizedFusedMoEMethod.maybe_make_prepare_finalize() returns None when AITER is the backend, which silently skips MORI dispatch/combine. Tokens never get sent to remote GPUs, each GPU only runs its local experts, dropping ~87.5% of expert contributions on EP8. The model appears to work but produces degraded output.
Three changes:
unquantized_fused_moe_method.py: Remove the AITER opt-out in maybe_make_prepare_finalize() so MoriPrepareAndFinalize is created via all2all_utils.py. Also add AiterExperts as a valid return from select_gemm_impl() when the backend is AITER.
all2all_utils.py: Handle unquantized MORI handle creation. For unquantized models, quant_config.quant_dtype is None which crashes MORI init. Use moe.in_dtype (BF16/FP16) and scale_dim=0 when FP8 dispatch is not active.
layer.py: Add a validation guard: if mori/deepep/nixl backends get None from maybe_make_prepare_finalize(), raise ValueError instead of silently falling back to local-only execution.
