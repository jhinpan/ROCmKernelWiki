# [ROCm] Widen AITER fused AR RMSNorm 1-stage gate

**Repository:** [vllm-project/vllm](https://github.com/vllm-project/vllm) · **PR:** [#42409](https://github.com/vllm-project/vllm/pull/42409) · **Merged:** 2026-05-15 · **Author:** @akii96

**Inclusion reason:** kernel path 'vllm/_aiter_ops.py'; keyword 'attention'

## Summary (from upstream PR description)

Purpose
Replace the hardcoded hidden_dim allowlist used for AITER fused allreduce+RMSNorm 1-stage dispatch with the kernel's actual pack-size constraint.
Today, vLLM only enables the AITER 1-stage AR+RMS path for this fixed set of hidden sizes: 512, 1024, 2048, 4096, 7168.
That allowlist is narrower than the kernel constraint and excludes valid model shapes. One concrete example is GPT-OSS, where the relevant hidden size is 2880.
With bf16/fp16 activations, AITER's 1-stage path uses 16-byte vectorized packs:
The predicate mirrors dispatchFusedAllReduceRMSNorm in AITER v0.1.13, the version pinned by docker/Dockerfile.rocm_base:
https://github.com/ROCm/aiter/blob/cdcfa833bdf554ca75594c90dde4316ea9b50199/csrc/include/custom_all_reduce.cuh#L2553-L2554

pack_size = 16 / sizeof(T)
pack_size = 16 / 2 = 8

For GPT-OSS:

hidden_dim = 2880
2880 % 8 == 0
2880 / 8 = 360 <= 1024

So hidden_dim=2880 satisfies the 1-stage kernel constraint, but the previous hardcoded allowlist still forced it away from that path.
This PR changes only the hidden_ok predicate. The existing token_ok and size_ok gates are unchanged, so 1-stage dispatch is still limited by the same token-count, world-size, and message
