# [ROCm] Restore fast top_k_per_row kernels for sparse MLA when topk_tokens=2048

**Repository:** [vllm-project/vllm](https://github.com/vllm-project/vllm) · **PR:** [#42072](https://github.com/vllm-project/vllm/pull/42072) · **Merged:** 2026-05-15 · **Author:** @frida-andersson

**Inclusion reason:** kernel path 'vllm/v1/attention/ops/rocm_aiter_mla_sparse.py'; keyword 'attention'

## Summary (from upstream PR description)

Summary
#40871 replaced the C++ top_k_per_row_decode / top_k_per_row_prefill kernels with a generic torch.topk-based fallback (_topk_indices_torch) in rocm_aiter_sparse_attn_indexer_native, so that non-2048 topk_tokens values needed for DeepSeek-V4 would work. The fallback runs an unfused torch.topk + torch.where + dtype cast over a [num_tokens, max_model_len] logits tensor on every prefill chunk and every decode step — significantly slower than the specialized kernels.
On DeepSeek-V3.2 TP4 (MI355X) this regresses TPOT meaningfully (~26 ms vs ~18 ms in our internal benchmarks).
Fix
DeepSeek-V3.2 uses topk_tokens == 2048, which is exactly the value the specialized C++ kernels were written for. Route topk_tokens == 2048 back to torch.ops._C.top_k_per_row_prefill / torch.ops._C.top_k_per_row_decode, and keep _topk_indices_torch as the fallback for other topk_tokens values used by DeepSeek-V4.
Updates

Split fast-path dispatch into _topk_indices_prefill / _topk_indices_decode helpers (review feedback)
Decode path now slices topk_indices_buffer[:num_padded_tokens, :topk_tokens] to match the kernel's row count when requires_padding is true (Gemini review)

Test plan

DeepSeek-V3.2 TP4 on
