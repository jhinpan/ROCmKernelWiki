# [ROCm][Bugfix] Fall back from CK MXFP4 MoE when GEMM dimensions are unsupported

**Repository:** [vllm-project/vllm](https://github.com/vllm-project/vllm) · **PR:** [#35893](https://github.com/vllm-project/vllm/pull/35893) · **Merged:** 2026-03-04 · **Author:** @ChuanLi1101

**Inclusion reason:** kernel path 'vllm/model_executor/layers/quantization/mxfp4.py'; keyword 'gemm'

## Summary (from upstream PR description)

Summary
Fix a RuntimeError crash when using AITER fused MoE with MXFP4 quantization on certain model/TP configurations where CK's pre-compiled GEMM kernel instances don't support the resulting matrix dimensions.
Root cause: CK's MXFP4 MoE GEMM kernels require intermediate_size / tensor_parallel_size to be a multiple of 256 (due to FP4 packing combined with CK tile size constraints). When this is violated — e.g. MiniMax-M2.1 (intermediate_size=1536) with TP=4 yields intermediate_size_per_partition=384 — AITER raises:
RuntimeError: wrong! device_gemm with the specified compilation parameters does not support this GEMM problem

Fix: Add dimension validation at initialization time in two code paths:

Quark MXFP4 path (QuarkOCP_MX_MoEMethod): detect incompatible dimensions and fall back to emulation mode (weight dequantization + bf16 GEMM)
Mxfp4Config path (Mxfp4MoEMethod): detect incompatible dimensions and fall back from CK to Triton backend

Both paths log a clear warning when the fallback is triggered.
Fixes #35637
Test plan

With MiniMax-M2.1 MXFP4 on TP=4 (the failing config from the issue): model should load and serve without crash, using the emulation/triton fallback
With MiniMa
