# [ROCm] Fix MoE kernel test failures on gfx950

**Repository:** [vllm-project/vllm](https://github.com/vllm-project/vllm) · **PR:** [#37833](https://github.com/vllm-project/vllm/pull/37833) · **Merged:** 2026-03-25 · **Author:** @AndreasKaratzas

**Inclusion reason:** kernel path 'tests/kernels/moe/modular_kernel_tools/common.py'; keyword 'gemm'

## Summary (from upstream PR description)

Fixes ROCm-specific MoE kernel test failures on MI355 (gfx950).

gpt_oss_triton_kernels_moe.py: Handle installed triton_kernels.topk returning tuple instead of SparseMatrix in the expert_map code path
batched_deep_gemm_moe.py: Gate C++ persistent_masked_m_silu_mul_quant behind is_cuda() -- it is #ifndef USE_ROCM (no-op on ROCm). Uses Triton fallback instead. aiter#2420
fp8_utils.py: Use multiply-by-reciprocal (amax * (1/fp8_max)) in 3 Triton FP8 quantization kernels instead of division (amax / fp8_max) to avoid 1-ULP GPU fast-division error at FP8 quantization boundaries. Zero performance impact (compiles to same GPU instruction).
test_gpt_oss_triton_kernels.py: Handle topk tuple return; use routing_from_bitmatrix as reference (matches legacy_routing algorithm)
test_silu_mul_fp8_quant_deep_gemm.py: Platform-aware reference precision (bf16 for CUDA C++ kernel, f32 for ROCm Triton fallback); skip UE8M0 on ROCm; allow 1 FP8 quantum tolerance for tl.exp vs torch.exp ULP difference
test_modular_kernel_combinations.py: Add fe_supports_quant_scheme() to filter unsupported AiterExperts quant combinations (aiter#2419); relaxed tolerance for AITER FP8 hardware matmul vs f32 reference with ni
