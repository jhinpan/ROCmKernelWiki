## Summary (from upstream PR description)

(https://github.com/sgl-project/sglang/actions/runs/25454051067/job/74678649321)
The AMD CI VRAM cleanup script (scripts/ci/amd/ensure_vram_clear.sh) has been failing on shared self-hosted runners when a previous job leaves the GPU dirty. The most common signal is a RuntimeError: The memory capacity is unbalanced during init_torch_distributed, but in the worst case the runner ends up like this:
=== Initial GPU Memory Status ===
GPU[0..7]: GPU Memory Allocated (VRAM%): 94
=== Cleanup Attempt 1/3 ===
Killing SGLang processes...
✗ VRAM still not clear after attempt 1

i.e. all 8 GPUs uniformly at 94% — characteristic of a full TP=8 SGLang server still loaded after the previous job died abnormally. The current cleanup cannot recover from this for several reasons:

Attempt 1 is a near no-op in CI. It only runs pgrep -f 'sglang...' on the host, but host pgrep cannot see PIDs inside a container's PID namespace. Previous job's SGLang server lives inside a docker container, so this matches nothing.
Aggressive cleanup is gated to attempts ≥ 2. So the first attempt was always wasted on the most common failure mode.
