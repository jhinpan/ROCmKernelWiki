# [AMD] Dsv4/pr1 fix run time issue

**Repository:** [sgl-project/sglang](https://github.com/sgl-project/sglang) · **PR:** [#25898](https://github.com/sgl-project/sglang/pull/25898) · **Merged:** 2026-05-23 · **Author:** @kkHuang-amd

**Inclusion reason:** kernel path 'python/sglang/jit_kernel/csrc/deepseek_v4/c128_v2.cuh'; keyword 'gemm'

## Summary (from upstream PR description)

Co-authored-by: @1am9trash @RolaoDenthu @yichiche @hubertlu-tw @sogalin @HaiShaw @yctseng0211 @bingxche @amd-danli103 @Raiden-Makoto
Motivation
DeepSeek-V4 (DSV4) on AMD MI300X/MI350X GPUs encounters multiple runtime failures when serving inference workloads:


GPU fault (HSA_STATUS_ERROR_EXCEPTION) — The core CompressStatePool is initialized without swa_page_size, defaulting to 0. This causes division-by-zero in translate_from_swa_loc_to_state_loc(), producing out-of-bounds state_loc indices (e.g., 525448 vs buffer size 470528) that trigger a hardware exception during index_put_.


Model registration failure — fused_softmax_pool_triton is imported at module level in compress_hip.py but doesn't exist in the current deepseek_v4_rope.py, blocking DeepseekV4ForCausalLM class registration.


JIT kernel incompatibilities — Wave64 shuffle intrinsics, DLPack device type, FP8 conversion, and kernel launch APIs differ between CUDA and HIP.


Modifications
Commit 1: JIT kernel HIP/ROCm compatibility infrastructure
Adds HIP compatibility to JIT kernel shared headers for wave64 architectures:

warp.cuh: Use __shfl_xor/__shfl_up (HIP-native) instead of __shfl_xor_sync/__shfl_up_sync; 64-bit kFu
